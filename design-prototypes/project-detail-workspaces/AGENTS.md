# Prototype Instructions

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

## 本原型的业务边界（2026-09-12）

- 用户选择双工作区：项目执行、商务财务。原步骤栏不作为一级导航。
- 执行区使用现有“需求单 → 工作项”，不再用旧环节/任务；“项目资料”已移除，改为新增“项目提交内容”汇总入口。
- 项目提交内容从工作项的提交版本聚合，每个工作项默认最新版本，可展开历史版本；不建立新的项目资料实体。
- 两个概览只摘取有字段依据的现有模块摘要与入口，不添加完成率、风险评分或推测财务异常。
- 本项目数据快照取自 2026-09-12 只读查询。原型不写正式 src、API 或数据库。
- 项目信息保留顶部“编辑 / 删除”操作；项目状态标签放在标题旁。项目周期必须展示起止日期、自然日和工作日，并依据正式页的调休口径计算。标题下保持一行三列信息组，每组两项，第三列给项目周期更多横向空间；不恢复正式页的“基础信息 / 项目进度”分区。
- 左侧导航的图标、标题和计数各自对齐；各内容页只保留页面顶部一个主标题，不在下方卡片重复同名标题。人员信息沿用正式页按职能分组、添加成员和移除成员的交互；独立原型中的增删仅在浏览器内生效，不写正式业务数据。
- 原型页面应像正式业务页面一样展示，不在界面上放“原型操作仅在当前页面生效”“数据快照”“只读交互原型”等说明性标签；这类实现边界只保留在开发文档中。
- 旧版项目详情页用于核对业务字段、数据来源和必要操作，不作为新原型的交互或视觉规范。用户允许根据可用性优化布局、信息层级和操作路径；不要仅为“还原旧版”而照搬匆忙设计。
- 人员信息改为顶部集中“添加成员”、下方按职能分卡展示成员与明确的“移除”动作。添加使用可搜索、可多选的员工弹窗并按职能自动归组；移除保留确认。以便先看清团队结构，再执行人员管理操作。
- 已加入项目的离职成员继续显示并明确标注“离职”，排在同组在职成员之后；添加成员只列出在职且尚未加入该项目的员工，沿用正式页的业务规则。
- 里程碑内容优先采用纵向时间线，避免横向卡片折行打断日期顺序；保留类型、客户/项目/供应商参与人和详情。完成与未完成要有明显的颜色层级；已完成节点的会议方式、地点降为辅助信息。当前正式里程碑模型没有独立完成字段，原型里的状态对比只用于视觉评审，正式接入前不得把“日期已过”当作真实完成状态。
- 里程碑时间线按日期倒序，最近节点优先展示，向下查看更早的历史记录。
- 里程碑时间线左侧日期下方显示对应星期；日期范围显示开始日期的星期，未排期不显示星期。
- 已过日期的里程碑只用时间线圆点表达时间状态，卡片内不再重复显示“日期已过”或“已完成”状态标签；未来或当日节点仍可保留状态文字。
- 工时原型分为记录与分析两视图：记录保留事件与人员链接、编辑和删除操作，以事件单独搜索、人员单独筛选，并对全部记录分页；日期与时间采用上下两行。工时显示小时和折算天数，天数旁保留 Info 图标解释 7.5 小时基准及超过基准后按当日总工时分摊的规则。分析按全部记录汇总人员小时、折算天数和占比，图形仅用原生 CSS 横向条实现，不引入第三方图表库。全部 83 条明细已于 2026-09-13 从现有项目只读核对并保存在 `src/workEntries.snapshot.json`，原型内的编辑与删除只改变浏览器状态。
- 工时记录的“全部人员”筛选按职能分组，沿用人员信息里的项目组、设计组优先顺序；历史工时人员即使已离职或不在当前项目成员中也保留在筛选项。原型快照未收录职能且现有资料无法核实的人员归入“其他”，不猜测职能。
- 项目提交内容仍是工作项提交版本与反馈的项目级汇总，不另建实体。项目列表标清所属需求单与工作项，只显示最新版、提交信息、反馈有无及调整项/图片数量，不摘录反馈正文；打开宽抽屉后按“提交 → 反馈 → 调整项及图片”纵向阅读，避免三等分栏挤压长反馈。普通快照只用核实过的现有内容；`?richFeedback` 是用于检验长文、多调整项、多图片布局的独立视觉样例，不写入项目数据。该独立模块的最终展示方式暂缓决定。
- 多需求单场景在 `?submissionScenario=complex` 独立预览：项目提交内容按“需求单 → 工作项 → 版本”串联；需求单与工作项按最近提交时间倒序，无提交的需求单置底；每个工作项内按版本倒序切换，提交和对应反馈一起阅读。场景含 5 张需求单、8 个工作项、14 版提交及一张没有提交的需求单；长反馈中的图使用清楚的占位图块，不混入普通项目快照。
- 项目级提交汇总须在工作项行和版本切换处明确标出被指定为“最终版”的版本，不能让“最新版本”代替这一业务状态。最终版详情需突出源文件；该场景按用户要求把源文件作为最终版必交内容，没有源文件时显示待补状态。正式工作项目前仍按 `sourceFilePolicy` 区分必交/选交，后续正式接入时应核对用户的新规则是否替代选交策略。
- “项目提交内容”页的归组说明放在页面主标题下方；搜索框与需求单分组卡片直接排在内容区，不再用一层外围卡片包住整个模块。
- 执行概览的大数字卡片用简短的“状态＋数量”副文案：需求单和工作项分别统计“进行中 / 已完成 / 暂停”，数量为零的状态不显示，也不写“均进行中”。里程碑仅按日期展示“即将到来 / 今天 / 日期已过”的非零数量，不能将日期已过推断为业务已完成；本项目 18 条排期日期已于 2026-09-13 只读核对。
- “需求单 / 工作项”优先与正式项目排期页的共享组件保持一致：需求单按状态与时间排列，默认展开首张；内部按工作项列出状态、类型、审核人、执行人与计划工时，展开后显示工作描述、属性、交付时间和工作记录。正式项目详情页直接复用 `ProjectBriefProgressContent`，原型仅按 2026-09-13 只读核对的字段近似展示；完成工作项默认不出现在当前列表中，旧步骤组件保留供对照。
- 商务财务左侧将“成本追踪”和“项目报销记录”列为两个并列入口；旧 Step 内为容纳两者而设置的二级 Tab 不再作为新工作区的导航层级。原型内容按入口分别展示；正式页的成本追踪和项目报销记录已接入各自的工作区内容，旧步骤及操作继续保留。
- “项目报销记录”入口内结合“预算汇总 / 报销明细”两视图，并在切换时保留预算总额、累计已报销和剩余可报销三项摘要。汇总按当前财务结构的执行费用类别列出预算、已报销、剩余额度、使用进度和状态，正式页直接复用执行费用监控组件及其进度/状态口径，不另写汇总表；明细沿用正式项目详情的逐条报销字段与操作。2026-09-13 只读核对的演示项目目前 0 条报销，预算类别为加班打车 1000、快递费 100、外出打车 500、物料费 200、招待费 500 元；原型不得为填充表格而伪造实际记录。
- “添加报销”只放在“报销明细”视图的“实际报销明细”标题行右侧；预算汇总不显示该按钮。正式页复用原项目报销新增弹窗与权限；原型弹窗对照现有项目、申请人、类别、金额、发生日期字段，不写业务数据。
- “项目报销记录”页面标题上方不显示“商务财务 / 项目报销记录”面包屑，保持与新版项目执行页一致；执行费用预算卡片的金额下方展示当前财务结构中的执行费用类别彩色标签，颜色与立项页同一执行费用选项保持一致，不放“来自项目财务结构”之类的来源提示。
- 预算汇总的类别表不重复“总计”行；上方“累计已报销”卡片的副文案只显示实际报销记录条数，不显示整体使用进度百分比。正式页仅在嵌入项目报销工作区时隐藏监控组件的总计行，独立执行费用监控页保留原总计。
- 成本追踪先在独立原型评审，获确认后已接入正式商务财务工作区，复用原实时成本组件的计算、明细与操作。`?costPreview=1` 直达当前大理项目的成本追踪原型；以 2026-09-13 从旧“实时成本”页核对的数值展示工作日、收入、总费用、利润及原表五列与全部分组行。表内不再重复项目名，因为页面顶部已经显示；页面标题上方也不放面包屑，与项目报销记录一致。保留收入、成本、利润、比例条、备注和计算口径，用更贴近双工作区的摘要卡与浅色分组样式供评审。
- 商务财务侧栏保留每项标题右侧的关键信息：报价测算和项目立项显示实际版本，收付款显示应收 / 应付计划数；成本追踪显示自动计算或人工录入口径，项目报销记录显示实际记录条数。原型使用已核对的静态快照，正式页从项目与现有接口取实时数据；取数失败时不伪造数量。

- 报价测算保留“成本测算 / 报价参考”两个内层视图。成本测算由项目经理填写客户报价、预计工作日、成员和各自投入占比，以及中介、外包与执行费用需求；逐人成本沿用原表权限，财务、HR、管理员可见，项目经理不可见。报价参考先复用原卡片，具体呈现仍待逐项核对。当前项目 v1 的 5 位成员、40 个工作日及目标报价参考于 2026-09-13 只读核对。`?quotePreview=manager` 与 `?quotePreview=finance` 用于分别评审两种视角；静态原型的 URL 参数不是权限控制，正式接入必须在服务端按原角色规则过滤敏感数据。
- 报价测算的成本测算顶部仅放原有“客户报价(不含税)”和“预估时长”两张数据卡，不放测算人、参与人数或“项目经理填写”等新增说明，也不再给两张卡套一个重复标题的外框。项目经理的“生成同步信息 / 更新成本测算”放在“成本测算 / 报价参考”切换行右侧；线上不显示“项目经理视角”等角色预览标签。
- 成本测算里的人员配置保留新版独立外框；下方费用信息沿用原 `InfoGrid` 的分组与字段：中介费用（费率、预估中介费）、外包费用（总额、明细、备注）、执行费用（类别，存在“其他”时另显备注）。不要因原型摘要化而丢字段。2026-09-13 用户澄清逐人成本权限沿用原代码：FINANCE、HR、ADMIN 均可见，不调整该逻辑。

Build app UI in `src/`. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run build` and `npm run test:sites`; the build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.
